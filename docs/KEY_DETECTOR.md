# Оставленный ключ: локальная экспериментальная проверка

## Причина пропуска и исправление

До 18.10.2026 `key_left_in_lock` имел режим `manual_review`: общего распознавания
ключа не было, поэтому система не могла сформировать такое событие. Теперь
включён отдельный `automatic_candidate` для различимой области замка на известной
камере. Поворот ключа и факт запирания по-прежнему не распознаются.

Пользователь подтвердил пару: видео 22 — ключ оставлен, 23 — правильное действие.
В рабочих решениях номера, имена файлов, порядок загрузки и готовые ответы не
используются. Разметка используется только при разработке и проверке.

## Как работает

1. Область границ шкафа сопоставляется с эталоном с ограниченным сдвигом и поправкой
   на яркость. Несовпадение ракурса, недостаточное разрешение или плохой кадр дают
   неизвестное состояние, а не «ключ вынут».
2. Сравнивается маленькая область замка с образцами «ключ вставлен / ключ вынут».
   Различительные веса ограничены окрестностью ключа. Стол, экран компьютера,
   одежда и остальной фон не используются для выбора класса ключа. Нужны малое
   расстояние до эталона и достаточное отличие от противоположного состояния.
3. Перекрытие области человеком запрещает классификацию. Для события требуются
   предварительное присутствие человека у сейфа/рабочего места, движение в зоне
   выхода и устойчивый признак ключа минимум 3 секунды без сотрудника/посетителей
   в соответствующих зонах. Разрыв кадров и неизвестное состояние сбрасывают
   накопление. Три секунды — инженерный порог, не нормативный срок.
4. API возвращает `key_left_in_lock`, таймкод, три настоящих кадра и контекст
   правила. При неразличимом состоянии — `insufficient_evidence`, не успешная
   проверка отсутствия ключа.

Файлы: `forte/key_state.py`, `config/key_calibration.json`, `tests/test_key_state.py`.
Модуль использует уже установленные NumPy/Pillow; новые веса и облачные API не нужны.

## Проверка на реальных видео

| Видео | Целевой результат | Полный локальный прогон |
| --- | --- | --- |
| 22 | Ключ после ухода | `key_left_in_lock`: 00:15, подтверждение 00:18; 34,72 с |
| 23 | Правильное действие | Событий нет; 29,33 с |

Отчёты: `outputs/key-validation/Х-22.json`, `Х-23.json` (локальные, не для Git).
Повторная загрузка через рабочий HTTP API с нейтральным именем файла подтвердила:
22 — тот же кандидат 00:15/00:18 и три кадра, 34,00 с; 23 — без событий, 29,17 с.
Отчёты `http22.json`, `http23.json` лежат в той же локальной папке.
Это **пара разработки**, не независимая оценка точности: для калибровки использованы
кадр 16 с видео 22 и кадр 14 с видео 23, затем обработаны полные видео.
Оставшиеся кадры тех же роликов не считаются независимым тестовым набором.

Дополнительная проверка изображений замка в 11, 24 и 25 не дала положительных
состояний: область не прошла проверку соответствия камере/шкафу и осталась
неизвестной. Это не доказывает отсутствие ключа и не является полным повторным
анализом этих видео. Для другого ракурса нужны новые крупные планы и отдельная
калибровка, а также независимые положительные и отрицательные ролики.

## Источник и ограничения

Пункт 80 постановления № 231 отсылает порядок обращения с ключами к внутренним
документам банка. Конкретное требование изъять ключ после ухода нужно подтвердить
таким документом. Карточка содержит это условие и ограничения. Визуальный кандидат
не доказывает ни незапертый сейф, ни установленное нарушение нормы.

Ключ занимает несколько пикселей. Модель может перепутать похожую деталь с ключом;
на незнакомой камере гарантии распознавания нет. Утверждать об универсальном
исправлении или измеренной точности на этой паре нельзя.

## Воспроизведение

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m scripts.evaluate_cases "C:\path\clip.mov" --out outputs\key-check
```

После обновления перезапустите `Start-Forte.cmd` и загрузите видео заново.
Готовые старые отчёты не пересчитываются. `scripts/check_local_upload.py` проверяет
загрузку через тот же API с нейтральным именем файла, не используя номер ролика.
